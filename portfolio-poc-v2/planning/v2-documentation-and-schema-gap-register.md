# V2 documentation and schema control gap register

**Review date:** 10 November 2026  
**Scope:** Current working tree of `portfolio-poc-v2`, English Core and SRS, and `output/BHSS expected inputs and outputs.docx`.  
**Status:** Internal analysis and recommendations; not BHSS or JC approval. The Core document remains the authoritative relationship model. Proposed additions below are not school decisions.

## Purpose and reading guide

This register identifies missing or unclear specifications, implementation gaps, and discrepancies that matter when extending v2. It is not a claim that the SRS or Core contain no relevant requirement: each item states whether the gap is in the **documentation**, **implementation**, **both**, or needs **verification**. A table or endpoint alone does not establish that a full workflow works. This is a targeted static review, not a complete requirement-by-requirement acceptance test or security audit. The working tree contained pre-existing changes when reviewed; line references may move.

The previously published `portfolio-poc-v2/srs-implementation-gap.md` is dated 29 October and is useful historical context, not a current closure report. V2 now has additional rubric and Portfolio-template code. Do not infer that every manifest CSV is an operational import. `server/services/dataOperationsService.js` exposes several exports; the existence of those headers does not prove corresponding import/commit workflows.

**Priority:** P0 = prerequisite for safe, correct operation of the stated slice; P1 = needed for a usable MVP slice or governance; P2 = later/conditional. Priorities are planning recommendations, not delivery commitments.

## Confirmed model and proposed direction

The current Core requires separate identity, scoped role/capability assignment, activity/revision, form/version, evidence/proof, rubric/version and Portfolio/version relationships. The role, rubric, form and Portfolio already have version concepts. Activity templates exist in Core, but an explicit pinned immutable activity-template version and spreadsheet contract are proposed, not a confirmed architectural rule. Academic-result schema and source-specific parser management are proposals, not BHSS-approved requirements. Spreadsheet-only use for all review actions is open; do not remove the current in-app workflows by assumption.

### Template and contract distinctions

| Concept | Responsibility | Current evidence | Needed design decision |
|---|---|---|---|
| Role template | Defines capabilities, not a person's job title or scope | Core role-version and `user_role_assignments`; `server/repositories/schema.js` role tables | Administration, publication, migration and spreadsheet contract |
| Rubric template | Defines label/assessment axes, levels and conditions | Core rubric section; `server/services/rubricService.js` five sheets | Resolve SRS discrepancy; verify completeness and isolation |
| Activity template | Reusable defaults for an activity, distinct from an activity revision | Core activity template ERD; v2 `activities.activity_template_id` | Explicit version/pinning and how defaults are copied |
| Form template | Versioned questions and audience blocks, distinct from responses | Core form definition/response rules; schema form/question tables | Complete governed round trip and response imports |
| Portfolio template | Semantic presentation structure, distinct from learner content | Core Portfolio template; `portfolioTemplateRepository.js` and `portfolioService.js` | Administration, scoped selection and pinning verification |
| Import contract/parser | Maps a specific file into validated domain commands; not a business template | `import_contract_versions`, import services and adapters | Supported source layouts, parser version, assignment and lifecycle |

## Proposed academic result contract for review

One row represents one student, subject, reporting period and assessment/result. Minimum proposed headers: `source_result_key`, `student_number`, `student_name` (identity check), `academic_year_code`, `reporting_period_code`, `subject_code`, `assessment_code`, `grading_scheme_code`, `numeric_result`, `grade_result`, `result_status`, `result_date`, `source_document_ref`, `remarks`. Student number, source key, period, subject, assessment, named scheme and status are required; numeric/grade value is conditional on scheme and status. Final identifiers, grade codes and whether both result values are allowed are open.

Proposed entities: existing `subjects` and `department_subjects`; optional `subject_source_codes`; `grading_schemes` and immutable versions/allowed values; `assessment_definitions`; stable `academic_results`; append-only `academic_result_revisions`; and links to existing import batch/record custody. Ensure same-school references and validate named scale, duplicate key and explicit correction. Missing or absent is not zero. Academic grades remain supporting evidence and never automatically become a framework step. A result paper and its real field definitions are needed before a parser or final contract can be approved.

## Recommended execution sequence

1. **Baseline and ownership:** reconcile the five-sheet SRS discrepancy; inventory actual v2 APIs, contracts, tests and working-tree state; agree whether spreadsheet-only includes review actions.
2. **Schema controls:** establish data dictionary, ownership, school-scoped references, lifecycle and versioning; retain the explicit disposable-POC reset until a tested production migration strategy is approved.
3. **One academic-result vertical:** obtain a sanitized result paper; agree identifiers and grading scheme; implement one canonical workbook and, if needed, one dedicated source parser; test staged import, matching, correction and visibility.
4. **Template governance:** close activity-template version design and scoped rubric/Portfolio selection, then demonstrate role, rubric, form and Portfolio version behavior through changes to existing instances.
5. **Evidence to publication:** complete human proof review, official rubric results and Portfolio dependency correction/reissue, including consent and controlled exports.
6. **Traceability close-out:** record each requirement's implementation, tests, owner and remaining decision; update English and Hong Kong Traditional Chinese architecture/SRS together when an architectural decision is confirmed.
