# SRS-02 學校結構及學年時段

## 1. 目的

平台先維持清晰而穩定的學校資料邊界及學生身份；班別、級別、在校狀態、負責老師及產品功能開放狀態則按實際生效日期留下歷史。

## 2. 功能要求

| ID | 要求 | 狀態 | 階段 |
|---|---|---|---|
| SCH-FR-001 | 每名學生只有一個穩定的內部 `student_id`；班別及級別以有生效日期的紀錄處理。 | 建議架構 | P0 |
| SCH-FR-002 | 歷史紀錄須支援轉班、留級、離校及日後復學，而不改寫舊活動。 | 已確認工作模型 | P1 |
| SCH-FR-003 | 活動參加紀錄可按活動日期查出學生當時班別，同時保留直接的參加者關係。 | 建議架構 | P1 |
| SCH-FR-004 | 學年包含報告時段，並有清楚開始、結束及結算日期。 | 建議架構 | P1 |
| SCH-FR-005 | 轉年先預覽，分辨留校、新增、離校、轉班及未配對紀錄；確認後以單一交易套用。 | POC 對齊建議 | P1 |
| SCH-FR-006 | 時段結束或 Portfolio 發布後，日後改班也不可影響舊快照重現。 | 已確認架構 | P1 |
| SCH-FR-007 | 跨年、重疊及截止日規則維持可設定。 | 政策待定 H-08 | P1 |
| SCH-FR-008 | 職員輸入活動開始／完結日期後，伺服器須找出完整涵蓋該範圍的單一匯報學段。 | 已確認 L-09；10 月 26 日修訂 | P0 |
| SCH-FR-009 | 活動跨越兩個學段時須建立例外；拆分活動或由獲授權人員明確批核前，不可繼續。 | 已確認 L-09；例外批核權待定 | P0 |
| SCH-FR-010 | 每種部署均須保存穩定的 `schools.school_id`。即使是單校本地部署，也應建立一筆已設定的學校紀錄，不可省略學校邊界。 | 系統分析架構決定已批准（2026-10-27） | P0 |

| SCH-FR-012 | 產品功能目錄須為每項功能定義穩定 `feature_key` 及生命週期（`development`、`pilot`、`released`、`retired`）；按校功能政策則記錄該校的有效狀態（`disabled`、`pilot`、`enabled`）及審計資料。 | 系統分析架構決定已批准（2026-10-27） | P1 |
| SCH-FR-013 | 開發中、試行中及未識別的功能預設不可使用；只有獲授權的平台政策明確開放後，相關學校才可使用。 | 系統分析架構決定已批准（2026-10-27） | P1 |
| SCH-FR-014 | 按校功能政策須容許示範學校只試用已準備好的功能，同時隱藏及封鎖未完成部分；功能開放絕不可繞過角色、工作範圍、生命週期、同意或批核控制。 | 系統分析架構決定已批准（2026-10-27） | P1 |
| SCH-FR-015 | `SchoolId` 是不包含業務意思而且不可變更的 domain 識別碼，在資料庫保存為 `school_id`；不可由可修改的學校名稱／代碼推算，並須放入登入工作階段、背景工作及審計脈絡。 | 系統分析架構決定已批准（2026-10-27） | P0 |
| SCH-FR-016 | 學校須維護可版本化的部門及科目定義；科目可透過有生效日期的關係隸屬一個或多個部門。 | 系統分析架構決定已批准（2026-10-28） | P1 |
| SCH-FR-017 | 教職員群組成員關係須有生效日期，並獨立於職位及功能角色分派，讓學校可按教師群組套用政策或活動可見範圍。 | 系統分析架構決定已批准（2026-10-28） | P1 |
| SCH-FR-018 | 教職員職位定義及用戶職位任命須屬於學校、有生效日期及可供搜尋，但不可直接授予內容操作權。 | 系統分析架構決定已批准（2026-10-28） | P1 |
| SCH-FR-019 | 教職員功能分派可引用部門、科目、級別、班別、群組、課程、活動或學生範圍；日後更改範圍不得改寫歷史操作。 | 系統分析架構決定已批准（2026-10-28） | P1 |
| SCH-FR-020 | SchoolAdmin 套用有審計紀錄的全校權限政策修訂前，須可預覽受影響用戶。 | 系統分析架構決定已批准（2026-10-28） | P1 |

## 3. 主要資料

| 資料 | 必須內容 |
|---|---|
| 學校 | 穩定學校 ID／代碼、顯示名稱、運作模式（`production`、`demo`、`test`）、停用狀態／原因／操作人／時間 |
| 功能定義 | 穩定功能鍵、說明、生命週期、預設可用狀態及時間 |
| 按校功能政策 | 學校、功能鍵、可用狀態、可選生效期／原因、設定人及時間 |
| 用戶 | 穩定 ID、學校、姓名、帳戶狀態、建立／封存時間 |
| 學生資料 | 穩定學生編號、入學資料、從歷史推算的目前狀態 |
| 學年／報告時段 | 編號、名稱、開始／結束／結算日期、狀態 |
| 班別 | 所屬學年、班別代碼／名稱、級別、狀態 |
| 班別紀錄 | 學生、班別、生效期、原因、來源、處理人 |
| 在校狀態 | 在校／離校／復學／停學、生效期及原因 |
| 教職員分配 | 用戶、班別／活動／課程、職責、生效期 |
| 部門 | 學校、穩定代碼／名稱、狀態、生效期 |
| 科目 | 學校、穩定代碼／名稱、狀態、生效期 |
| 部門－科目關係 | 部門、科目、生效期 |
| 教職員群組／成員 | 群組、用戶、成員職責、生效期 |
| 教職員職位任命 | 用戶、職位定義、生效期；只作描述 |
| 功能角色分派 | 用戶、功能角色、範圍類型／ID、生效期及分派人 |

## 4. 欄位規則

| 欄位 | 必填 | 最小值 | 最大值／規則 |
|---|---|---:|---|
| 學生編號 | 是 | 1 個字元 | 64 個字元；權威來源待定 L-03 |
| 班別／學年／時段代碼 | 是 | 1 | 64 個字元 |
| 顯示名稱 | 是 | 1 | 200 個字元 |
| 級別 | 是 | 1 | 臨時上限 20；非數字命名可用設定代碼 |
| 開始／結束日期 | 是 | — | 開始不得遲於結束 |
| 同一日主要班別 | 是 | 0 | 最多 1 個；例外須審計 |
| 轉年批次 | 否 | 1 | 5,000 行 |
| 改動原因 | 修正／轉班時必填 | 1 | 4,000 個字元 |
| 學校代碼 | 是 | 1 | 64 個字元；不可重複 |
| 學校運作模式 | 是 | — | `production`、`demo`、`test` |
| 功能鍵 | 是 | 1 | 128 個字元；穩定的機器可讀代碼 |
| 功能可用狀態 | 是 | — | `disabled`、`pilot`、`enabled` |

有效功能狀態按以下次序計算：學校整體停用時一律封鎖；已退役或未知功能一律封鎖；校本 `disabled` 明確覆蓋所有預設值；開發中／試行中功能必須由校本政策明確設為 `pilot` 或 `enabled`；正式功能如沒有校本覆蓋，才可採用功能目錄的預設值。每次改動均以追加方式保存審計紀錄。

    Upload[上載新時段名單] --> Validate[驗證身份及班別代碼]

## 6. 存取

- 學生只看本人現時班別及需要顯示的歷史標籤，不可瀏覽全班名錄。
- 老師只看有效功能分派及適用權限政策涵蓋的班別／學生。
- 職員按獲委派部門／科目／級別／班別／群組／課程範圍處理轉年。
- SchoolAdmin 管理學年、時段、部門、科目、班別、教職員群組、成員及轉年。
- SchoolAdmin 可查看有效功能政策，並只可在獲委派範圍內提出／設定變更。重新啟用整間已停用學校須由平台營運權限處理，不能單憑一般 SchoolAdmin 角色執行。

## 7. 驗收情境

- 學生由 2B 轉至 2C 後，ID 不變，2B 舊活動仍然保留。
- 學生離校兩年後以較低級別復學，只新增歷史紀錄，不建立新身份。
- 老師工作分配完結後失去存取權，除非另有歷史覆核授權。
- 未解決重複學生編號前，不可套用轉年。
- 活動完整落在 `2025-26-P1` 時由系統自動歸入該學段，職員不可手動改選。
- 活動跨越 P1 及 P2 時，須先拆分或明確批核例外並留下審計紀錄。
- 單校本地部署與多校服務均採用相同 `school_id` 關係，即使本地部署只有一間學校亦不例外。
- 示範學校可使用一項獲明確開放的試行功能，而另一項仍在開發的功能繼續不可使用。
- 更改老師職銜不會自行增加或刪除內容權限；須另行變更相應功能角色／權限分派。
- 老師退出英文科部門後，自生效日起失去日後部門範圍存取，但先前審計操作不會被改寫。
